# Knowledge Base Usage Guide

> 模板来源：PowersNexus OpenSpec
> 用途：项目知识库的使用方法和最佳实践

---

## 什么是项目知识库

项目知识库是 PowersNexus 的"记忆系统"，沉淀项目过程中的经验教训、最佳实践、常见陷阱和可复用模式，让后续开发站在前人的肩膀上。

**核心价值：**
- 🧠 **避免重蹈覆辙** - 犯过的错误不再犯第二次
- 🚀 **加速开发** - 直接复用成熟模式和实践
- 📈 **持续改进** - 每做完一个项目，能力就上一个台阶
- 🎯 **质量保障** - 常见问题在设计阶段就能发现

## 各阶段如何使用知识库

### 1. Brainstorming / 设计阶段

**读取：**
- 📖 读取 `lessons-learned.md` 了解项目历史
- 📖 读取相关领域的 `best-practices/*.md`
- 📖 读取相关的 `common-mistakes/*.md` 避免踩坑
- 📖 检查 `patterns/` 中是否有可复用的模式

**写入：**
- 如果发现了新的设计模式 → 记录到 `patterns/`
- 如果有重要的架构决策 → 可以标记为最佳实践候选

### 2. 开发实施阶段

**读取：**
- 遇到问题时 → 检查 `common-mistakes/`
- 写测试时 → 参考 `best-practices/testing.md`
- 写 API 时 → 参考 `best-practices/api-design.md`

**写入：**
- 踩到了新的坑 → 记录到 `common-mistakes/`
- 发现了好的做法 → 记录到 `best-practices/`

### 3. Finishing / 复盘阶段

**读取：**
- 读取整个知识库，对比本次项目的表现

**写入：**
- ✅ 添加本次项目的经验教训到 `lessons-learned.md`
- ✅ 复盘报告存入 `retrospectives/`
- ✅ 更新 `best-practices/` 和 `common-mistakes/`
- ✅ 如果有新模式 → 添加到 `patterns/`

## 知识入库标准

### ✅ 应该入库的内容

**最佳实践：**
- 经过验证的、可复用的技术方案
- 能显著提升质量/效率的做法
- 有具体示例和代码的模式

**经验教训：**
- 导致过 Bug 的设计或实现
- 造成过返工的决策
- 有具体场景和解决方案的

**可复用模式：**
- 跨项目通用的架构模式
- 有完整设计文档的解决方案
- 包含利弊分析的方案选型

### ❌ 不应该入库的内容

- 太具体的业务逻辑（只对特定项目有用）
- 未经验证的想法或假设
- 过于琐碎的细节（命名、格式等）
- 临时的、一次性的解决方案

## 知识条目格式

### 最佳实践条目格式

```markdown
## [实践名称]

**适用场景：** [什么时候应该用这个]
**解决的问题：** [解决了什么痛点]

### 具体做法

[详细描述]

### 代码示例

```
[示例代码]
```

### 为什么这样做

[原理解释]

### 反模式（不要这样做）

[常见错误做法]
```

### 经验教训条目格式

```markdown
## [教训名称]

**严重程度：** 高/中/低
**发生场景：** [在什么情况下会遇到]
**造成的影响：** [导致了什么问题]

### 问题描述

[详细描述问题]

### 根本原因

[分析为什么会发生]

### 解决方案

[怎么解决的]

### 预防措施

[以后怎么避免]
```

## 知识库质量保障

1. **定期整理**：每完成 3-5 个项目后，整理知识库，去重、分类
2. **质量审查**：重要知识条目需要经过至少一次红队审查
3. **过时标记**：不再适用的知识要标记为「已过时」并说明原因
4. **版本标注**：标注知识适用的技术栈版本，避免误导

| 阶段 | 读取 | 写入 |

| Brainstorming | ✅ 自动读取相关知识 | ⚠️ 发现新模式时建议写入 |

**知识库是 PowersNexus 持续改进的核心**——每完成一个项目，整个系统的能力就会变得更强。
