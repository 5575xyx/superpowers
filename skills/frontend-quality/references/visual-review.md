# 视觉审查协议

UI 任务完成后，审查者必须审查实际运行页面，而不是只阅读代码差异。

## 审查输入

- 设计契约或 `design-system/<project-slug>/MASTER.md`。
- 可访问的预览 URL、启动命令或桌面/移动端截图。
- 目标页面、关键交互与已知限制。

若无法获得预览或截图，记录为重要缺口；不得仅凭 diff 宣称视觉质量已通过。

## 最小检查矩阵

| 视口 | 必查内容 |
|---|---|
| 桌面（约 1440px） | 信息层级、内容宽度、栅格、主操作、空白与对齐 |
| 移动端（约 390px） | 无横向滚动、内容优先级、触控间距、固定元素遮挡 |

按需求额外检查深色模式、长文本、空/加载/错误状态和键盘焦点。

## 审查维度

每项标记通过、需修复或不适用，并提供截图或具体元素证据：

1. 设计契约一致性：令牌、字体、图标、圆角、阴影和色彩语义一致。
2. 视觉层级：一个明确主操作，标题、正文、辅助信息和危险操作有清晰层级。
3. 响应式：两个视口均无重叠、截断、横向滚动或固定元素遮挡。
4. 状态完整性：交互、加载、空、错误、禁用和成功反馈符合当前功能。
5. 可访问性：键盘焦点可见、语义与标签完整、状态不只依赖颜色。
6. 打磨度：无 emoji 结构图标、无随机硬编码样式、留白和对齐不显杂乱。

## 输出格式

```markdown
### UI 审查证据
- 预览：……
- 桌面证据：……
- 移动端证据：……

| 维度 | 结论 | 证据或问题 |
|---|---|---|
| 设计契约一致性 | 通过 / 需修复 / 不适用 | …… |
| 视觉层级 | 通过 / 需修复 / 不适用 | …… |
| 响应式 | 通过 / 需修复 / 不适用 | …… |
| 状态完整性 | 通过 / 需修复 / 不适用 | …… |
| 可访问性 | 通过 / 需修复 / 不适用 | …… |
| 打磨度 | 通过 / 需修复 / 不适用 | …… |
```

任一“需修复”项必须在合并前解决；没有视觉证据的 UI 任务不能标记为准备合并。
