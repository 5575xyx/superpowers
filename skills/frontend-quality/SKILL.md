# 前端质量

将界面从“能用”推进到“清晰、一致、可验证”。本技能不绑定框架或组件库；优先复用项目已有的设计系统。

方法论参考 UI/UX Pro Max（MIT）：采用其设计系统优先、响应式、状态完整性与交付前视觉检查的原则；不复制其代码、数据集或框架绑定实现。

## 使用时机

- 用户要求新增、重做或明显修改用户可见界面。
- 任务涉及页面布局、组件样式、导航、表单、数据展示、深色模式或移动端体验。
- 用户反馈“页面丑”“不专业”“不统一”或“移动端不好用”。

纯接口、后端、脚本或不可见的行为调整不使用本技能。

## 工作流

### 1. 先读取现有视觉语言

在写 UI 前检查：现有页面、组件库、CSS/Tailwind 配置、主题变量、图标集、字体和截图。已有模式优先于新建模式。

当 `ui-ux-pro-max` 已安装在本插件中时，先调用它生成或检索设计依据；再把结果固化为本技能要求的设计契约。不要跳过设计智能直接凭直觉挑选色彩、字体或布局。

若项目没有视觉系统，创建一份随功能提交的最小设计契约；不要直接在组件中散落任意色值、间距和阴影。

### 2. 写出设计契约

在设计文档或实施计划中明确以下内容：

| 维度 | 必须决定的内容 |
|---|---|
| 产品语气 | 目标用户、信息密度、视觉风格与一个主操作 |
| 布局 | 内容层级、容器宽度、网格、移动端优先的断点策略 |
| 令牌 | 颜色语义、字号层级、间距刻度、圆角和阴影层级 |
| 组件 | 使用或新增哪些组件；默认、悬停、焦点、禁用、加载、空和错误状态 |
| 内容 | 使用真实或接近真实的文案、数据长度、图片比例与空状态 |
| 无障碍 | 键盘路径、焦点可见性、语义结构、图标标签和对比度 |

若选择新视觉方向，先给出 2–3 个方向及取舍。布局或风格存在主观选择时，使用 Visual Companion 或可访问的浏览器预览展示对比；获得选择后再实现。

### 3. 按系统实现

- 使用语义化令牌或项目主题变量，避免组件内堆积硬编码视觉值。
- 复用现有组件与单一图标体系；不要用 emoji 充当产品图标。
- 采用移动端优先布局，确保窄屏没有横向滚动。
- 每个异步或可交互组件都实现加载、空、错误、禁用和成功反馈中适用的状态。
- 以尺寸、留白、字重和对比度建立层级，而不是依赖装饰性渐变或随机阴影。
- 动效仅表达状态或空间连续性，并尊重减少动态效果偏好。

### 4. 视觉验收

实现后在浏览器或项目已有预览环境中检查至少一个桌面宽度和一个移动宽度。对照 [验收清单](references/acceptance-checklist.md) 和 [视觉审查协议](references/visual-review.md) 逐项验证，并把截图路径、预览链接或人工审阅结论记录到任务结果中。

发现视觉缺陷时，先修复设计契约或组件规则，再修复单个页面；不要通过局部补丁制造新的不一致。

## 与 PowersNexus 流程集成

1. `brainstorming` 获得整体设计批准后：若任务含用户界面，先调用 `ui-ux-pro-max`，再调用本技能形成视觉契约。
2. `writing-plans` 必须把视觉契约和验收项映射为实现与验证任务。
3. `subagent-driven-development` 与 `requesting-code-review` 的实现审查必须检查视觉契约是否被落实，并输出视觉审查证据；完成前执行视觉验收。

## 交付格式

在任务文档中提供简短的“界面质量摘要”：

```markdown
### 界面质量摘要
- 视觉方向：……
- 复用的系统：……
- 响应式策略：……
- 状态覆盖：……
- 验收证据：桌面 ……；移动 ……；无障碍 ……
```
